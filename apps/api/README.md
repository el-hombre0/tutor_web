# Tutor API

NestJS API приложения. Для локального запуска из корня репозитория:

```bash
pnpm install
pnpm dev:api
```

При локальном запуске Nest CLI загружает корневой `.env`. По умолчанию сервер слушает порт `3001`; его можно изменить переменной `API_PORT` (целое число от 1 до 65535). В других окружениях переменная передаётся процессу при запуске.
`GET http://localhost:3001/health` проверяет процесс API и подключение к PostgreSQL запросом `SELECT 1`:

- HTTP 200: `{"api":"up","database":"up"}`;
- HTTP 503: `{"api":"up","database":"down"}`.

Для проверки используются `POSTGRES_HOST` (по умолчанию `127.0.0.1`), `POSTGRES_PORT` (по умолчанию `5432`), `POSTGRES_DB`, `POSTGRES_USER` и `POSTGRES_PASSWORD` из корневого `.env`. При запуске API в контейнере задайте `POSTGRES_HOST=postgres`.

Проверки из корня: `pnpm build:api`, `pnpm lint:api`, `pnpm test:api`, `pnpm test:e2e:api`.

## PostgreSQL и модель данных

API использует TypeORM и переменные `POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` из корневого `.env`. Перед запуском API запустите PostgreSQL: TypeORM устанавливает соединение при старте. Автоматическое изменение схемы отключено.

Из корня репозитория соберите API и примените миграцию:

```bash
pnpm build:api
pnpm --filter tutor-api migration:run
```

После изменений миграций сначала повторите сборку. Откат последней миграции — `pnpm --filter tutor-api migration:revert`; откат начальной миграции удалит созданные ей таблицы и данные. Интеграционную проверку в отдельной временной схеме можно запустить после сборки: `node --env-file=.env apps/api/test/database.integration.mjs` (пользователю БД нужно право создавать схемы).

Сущности описывают пользователей с несколькими ролями, пары репетитор–ученик, классы с несколькими репетиторами и учениками, а также сессии для будущей ротации refresh-токенов. Хеш пароля и хеш токена не выбираются в обычных запросах. Начальная миграция добавляет роли `admin`, `tech_admin`, `tutor`, `student`, `parent`. Проверку соответствия ролей при создании связей должна выполнять бизнес-логика; одних внешних ключей для этого недостаточно.

JWT, вход, хеширование паролей, проверка ролей и управление сессиями ещё не реализованы. Таблица сессий — только основа для будущей авторизации; токены и пароли в открытом виде хранить нельзя.

## Тестовые данные

Для локальной разработки после применения миграций выполните `pnpm build:api`, затем `pnpm --filter tutor-api seed:demo`. Скрипт добавляет семь пользователей четырёх ролей и два класса с участниками; повторный запуск не создаёт дубликаты. Он разрешён только для подключения к localhost и не работает при `NODE_ENV=production`.

Адреса пользователей имеют вид `demo.*@example.test`. У них нет рабочего пароля, поскольку авторизация ещё не реализована. Связь родителя с учеником пока не создана: соответствующей сущности в схеме ещё нет. Роль владельца `admin` из миграции сохраняется, но тестовый пользователь с ней не создаётся.
